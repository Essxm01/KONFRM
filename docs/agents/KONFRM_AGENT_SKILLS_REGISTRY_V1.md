## 1. Registry Overview

This registry provides the authoritative evaluation of all native KONFRM skills, active governed wrappers, and audited external candidate skills. Every entry is evaluated across 16 dimensions to ensure total compatibility with KONFRM architecture, DF2 design canon, token budgets, and security constraints.

### Recommendation Classes
- **`MANDATORY`**: Core operational skill required for specified roles.
- **`RECOMMENDED`**: Highly valuable domain accelerator, approved for active use within its profile.
- **`ON_DEMAND`**: Specialized tool loaded strictly when explicitly requested for a targeted task.
- **`EXPERIMENTAL`**: Under evaluation; isolated testing permitted, but not authorized for production workflows.
- **`USER_LEVEL_ONLY`**: Personal prompt/pacing preference; belongs in user client settings, never in repository.
- **`REJECT`**: Incompatible with KONFRM architecture, unsecure, or context-wasteful. Forbidden from repository.

## 4. Formal Conflict Log & Subordination Directives

### Conflict 1: Clean Architecture & BLoC in `flutter-apply-architecture-best-practices`
- **Upstream Pattern:** Recommends 4-layer Clean Architecture (Domain, Data, Presentation, Core) with mandatory UseCases, Entities separate from Models, and BLoC/Cubit state management.
- **KONFRM Canon:** Strictly enforces 3-layer Feature-First (`features/<feature>/presentation|application|data`), Riverpod without codegen, manual DTOs, and zero mandatory domain layer.
- **Subordination Directive:** The upstream skill is adapted via `konfrm-flutter-architecture`. The BLoC, Cubit, and Clean Architecture domain-layer sections are expunged. Riverpod state notifier patterns and feature-first directory conventions are substituted.

### Conflict 2: Rogue Directory Structures in `JuliusBrussee/Loop-Factory`
- **Upstream Pattern:** Creates `inbox/`, `active/`, `archive/` folders in repository root to manage tasks and reviews.
