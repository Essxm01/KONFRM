**KEEP all GitHub-published screenshots, visual review images, A56 frame captures, co-located reports/README/manifests, GitHub-readable JPEG Base64 companions, reference screen snapshots, and Flutter isolated preview source through completion of the full KONFRM application build, final application artifact export, and full release-preparation validation.** They are a required source of truth for turning isolated accepted Flutter previews into a coherent real app without visually rebuilding from zero or forgetting why earlier alternatives were rejected.

STOP any per-screen image deletion/archival-to-`trash`/mark-as-`TRASH_READY`/evidence-branch deletion once Founder visually approves a screen. Retain **V1, V2 and superseded/corrected iterations**, because they document reasoning, regression comparators and implementation acceptance tests. Treat even existing historically assigned `TRASH_READY` as ON HOLD if those images still exist.

## Priority / supersession

This NEW founder-approved directive explicitly SUPERSEDES all older GitHub task prompts, issue descriptions or relay/QA provisions with an evidence lifecycle `ACTIVE → REVIEWED → TRASH_READY → PURGED`, 'Base64 companions may be cleaned early', 'clean up evidence branch after Founder screen signoff', 'screen evidence is transient' or equivalent. Those older statements are *historical*, NOT current deletion permission.

New default evidence state: `RETAIN_UNTIL_FINAL_APP_EXPORT_AND_EXPLICIT_FOUNDER_CLEANUP_APPROVAL`.

Do NOT automatically delete or rename evidence images, folders, branches, historical screenshot filenames, preview-code snapshots, manifest/index/report, or their GitHub links. No one, including Bridge, Antigravity or assistants in future accounts/chats, may infer deletion authority from global completion of an isolated design task.

## What to preserve with each screen

- Exact screen ID, accepted revision and original/safe optimized true-device screenshots in each pertinent scenario; previous iterations and negative/regression case evidence.
- Full `REPORT.md`, `README.md`, `VISUAL_BRIDGE_README.md`, individually referenced, **actual remotely verified GitHub SHA/URLs** and decision/Issue trail.
- Co-located reproducible `review-source/*_preview_runner_*.dart`, fixture semantics and launch/readme, plus faithful ASCII Base64 JPEG image companions when used by Bridge.
- Canonical shared design tokens/logos/Cairo/RTL decisions as separate governing sources; screenshots/source are *review evidence*, not automatically production code.
- When later assembling production Flutter, map each approved screen to the actual production widget/route, documented interaction/backend contract and image-parity validation before calling it integrated.

## Exceptions and storage discipline

- **PUBLIC GITHUB PRIVACY OVERRIDES RETENTION OF UNSAFE PUBLIC CONTENT:** never upload raw unsanitized device images, private booking/customer data, unique physical-device serial, OTP, phone/email, secrets, auth/payment credentials, real banking values or private notifications. If any pre-existing published evidence exposes protected information, initiate the existing governed privacy/incident review for *specific* sensitive files, to contain exposure safely. Such security action is not permission for routine screenshot cleanup. Preserve a privacy-safe redacted reference when possible, with incident record.
- Continue optimizing **BEFORE upload** to preserve readability and keep repository lightweight; existing safe optimized images are kept, not replaced or discarded. Don't publish duplicate giant RAW images unnecessarily. Keep private full-resolution captures off public GitHub.
- Keep evidence folders on scoped evidence-only branches; no new merge into main to hoard images. If only copy is on evidence branch, PROTECT that branch by procedure and don't prune it.
- Temporary build outputs/caches can be cleaned only if they contain NO unique screenshot/Flutter design source/evidence. For image/preview-source artifacts already published to GitHub, this retention hold still applies.
